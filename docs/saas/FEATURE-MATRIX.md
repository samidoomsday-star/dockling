## Access rules used by every route

| Code | Meaning |
|---|---|
| O | Authenticated active workspace owner; member administration, commercial settings, connections, consent and job removal |
| E | Authenticated active workspace editor; create/process/review/export work within owner-approved policy |
| V | Authenticated active workspace viewer; read authorized job/source/current-output information, no mutation |
| P | MFA-authenticated platform administrator; operational/global configuration, without automatic document/key/billing access |
| S | Individually assigned, owner-approved, expiring support grant; read-only access to named jobs and approved data classes, checked on every request; no provider key access |
| W | Internal worker identity restricted to the leased operation, workspace, job, revision and artifact classes; not a browser role |
| U | Unauthenticated public access only to isolated fictional sample/help/about data |
| L | Owner's existing local CLI; its private filesystem storage is separate from hosted customer authorization |

O includes E and V rights; E includes V. P does not inherit O/E/V. Support grants never bypass data-deletion/revision checks and cannot access unrelated jobs, workspace-wide exports or connections. Platform access to customer exceptional operations needs both P and a valid owner-approved grant for the specific action; ordinary read-only S is insufficient. Expired/revoked membership or grant fails immediately.

Common authorization contract **A**: resolve identity/session and active workspace membership server-side; constrain every lookup/join/artifact to that workspace; private GETs do not reveal another workspace's ID or existence; writes additionally require CSRF, permission, expected revision when applicable and an audit actor. Re-fetch authorization at private download/page stream time. W claims do not allow unscoped enumeration. Public U must never query customer records. Rate/resource limits apply before expensive work.

Every row below requires **A**, plus its named feature-specific checks. Acceptance names describe tests to implement, not passed tests. Common negative suite **TENANT-DENY** tries list/search/direct ID/page/artifact/mutation from a different workspace, including worker inputs; **ROLE-DENY** tries writes as V, admin routes as O/E/V, and customer routes as P without a grant; **SESSION-DENY** covers absent/expired/revoked sessions and forged roles/CSRF. Apply these suites to every hosted row with a private read/write.

## Phase 1 permission acceptance fixture

Use synthetic workspace A and B, each with owner/editor/viewer, plus an MFA platform admin with no customer membership. Fixture IDs are opaque and externally meaningless. Test the cross-workspace record relationships, pagination cursor and job/file/operation IDs; altering the URL, request workspace field or role hint must not grant access. Exercise membership revocation while a session is active. A viewer may read A's current source/outputs but cannot edit, process, delete, consent, manage keys or buy. An owner can manage their workspace but cannot edit platform pricing, override hard resource bounds or inspect B. Admin has only redacted operational access until a valid scoped grant exists.

These are contract/acceptance definitions; Phase 1 and later phases must implement and run the applicable tests before marking the routes production-ready.
