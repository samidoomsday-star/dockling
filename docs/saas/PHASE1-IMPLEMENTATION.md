# SaaS foundation implementation and review

Phase 1 implements local synthetic infrastructure and the authenticated foundation; it does not make the product production-ready. Phase 2 moves actual intake/extraction into leased, isolated workers. Phase 3 connects review/exports. The full contract remains a versioned roadmap; unknown API routes return safe 404, never HTML or demo results.

## Boundaries

- Central `HostedSettings` validates explicit service origins/credentials. Local mode accepts loopback HTTP only. Production settings require HTTPS, and the database driver uses certificate-verifying TLS. This does not certify a deployment. Existing offline CLI configuration is independent.
- FastAPI hosts `/api/v1`, Authlib OIDC code/PKCE/state/nonce/signature/issuer/audience/time verification, and the API-mode React build. Only transient handshake data uses a signed cookie. The HttpOnly/SameSite server-session cookie is opaque; only its hash lives in PostgreSQL. Session expiry/revocation, Origin plus CSRF and active membership are checked server-side. No access/ID token or LLM key is stored in browser localStorage.
- Identity uses issuer+subject, not email. Invitation acceptance separately requires the invited verified email, expiry and a single-use token hash. Owner-only creation returns a fragment-based link. Tokens are derived with HMAC, allowing authorized idempotent replay without storing plaintext links in command history. Invitations do not send email or provision public user registration yet.
- Administrators require an allowlisted issuer subject **and** verified OTP/MFA AMR. Access expires after five minutes and requires another full sign-in. Realm OTP execution config attaches `default.reference.value=otp` with a 300-second age, and the maintained AMR mapper includes completed executions in the signed ID token. No hardcoded MFA claim is issued. Administrators have no customer membership by default.
- PostgreSQL is the hosted metadata authority. Alembic's frozen initial DDL creates identities, sessions, workspaces, memberships, invitations, jobs, events, idempotency records and artifact/operation skeletons. Child FKs include workspace+parent identity. Migrations use a separate owner; runtime uses `dockling_app` with DML but no schema ownership/superuser/DDL. The worker role has **no customer-table privileges** in this phase; leased scoped worker access is Phase 2. Session/audit retention and cleanup are release-hardening work.
- All private API lookups carry workspace identity. Mutation locks the workspace and rechecks live membership, serializing membership revocation, final-owner checks and idempotency. Repeated commands return the original recorded result; changed payloads with the same key conflict. Audit contains IDs/actions/revisions and does not record request contents or invitation email/token.
- Metadata read contracts have local-manifest and hosted adapters. Legacy CLI IDs remain date/channel strings checked by existing path confinement; hosted UUIDs are not forced into CLI manifests. The existing financial/parser/review/export core is preserved. **Only metadata reads are shared at this milestone; the complete pipeline command/UoW/worker adapter migration is Phase 2–3**, not a CLI subprocess wrapper or second hosted `order.json` authority.
- Private S3 access uses explicitly injected credentials and ignores SDK profile/shared-credential files. Artifact reads require current membership, workspace+job relationship, current revision, active deletion state and matching length/hash. There is no customer upload/download endpoint yet. Development storage is co-located in one container and accessible only on a host loopback port; worker egress isolation and presigned URLs are later work.
- API JSON inputs are bounded at 64 KiB, typed and reject unknown fields; pagination limits are at most 100 and cursor signatures bind resource/workspace. Safe errors never echo invalid fields, raw SQL, tokens or credentials. Private responses are no-store with CSP and no-referrer. Distributed throttling, cleanup, observability and deployment hardening remain Phase 6–7. Auth provider brute-force protection is enabled locally.
- Foundation UI obtains session/role/CSRF from the API, clears private query caches on workspace changes/logout, uses paginated jobs, and exposes owner team/preferences or MFA-admin health appropriately. Empty/unavailable states are truthful. It does not offer a browser role switch, fake conversions or a BYOK key entry before the secure gateway exists.

## Evidence and limitations

See `docs/PROGRESS.md` for the final run counts and `LOCAL-SETUP.md` for the receiving-device protocol. Real PostgreSQL/S3 integration checks and maintained-provider browser checks run separately from the original CLI gate. `tests_saas` is intentionally separate so installing the offline CLI alone does not require optional web services. The GitHub SaaS workflow supplies those services; it must not upload local credentials or identity traces. Local workflow execution is not proof of GitHub-hosted CI or Windows installation.

Phase 0's two-page OCR fixture still had two description mismatches despite exact financial checks. That evidence remains a requirement for source review. No customer statements, paid inference, billing, email, public hosting or production security certification are implied by this milestone.
